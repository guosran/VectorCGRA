═══════════════════════════════════════════════════════════════════════

The bicg.yaml at validation/test/bicg/bicg.yaml has SYSTEMIC ROUTING ERRORS.
The YAML was auto-generated with INCORRECT direction conventions.

KEY FINDINGS:

A) PHI_START BOOTSTRAP DEADLOCK:
   Tile 4 indices 1,2: PHI_START SOUTH, $8 → NORTH
   - SOUTH input = tile 0's NORTH output. But tile 0 only sends NORTH at step 8.
   - PHI_START at step 1 needs SOUTH data. Step 8 > step 1, so data comes from
     PREVIOUS iteration's step 8 — which doesn't exist for iteration 0.
   - PHI_START with first=1 reads recv_in[in0_idx] = SOUTH port → stalls forever.
   
B) MISSING ROUTES (tile4 → tile0):
   Tile 0 index 3: DATA_MOV NORTH → $0  (reads recv_data[NORTH])
   - recv_data[NORTH] = tile4.send_data[SOUTH]
   - BUT tile 4 NEVER sends via SOUTH port. It only sends NORTH (to tile8).
   - tile4.send_data[NORTH] → tile8.recv_data[SOUTH], NOT tile0!
   - RESULT: tile 0 waits forever for NORTH data that never arrives.

C) DIRECTION CONFUSION:
   tile 4's PHI_START output goes NORTH (to tile8), but the DATA consumer
   is tile0 (which is SOUTH of tile4). The YAML author confused NORTH/SOUTH
   for outputs.

D) SYSTEMIC ISSUE:
   tile 8 receives NORTH (from tile12) at steps 2,3,8 but tile12 has only
   2 operations (steps 0 and 8). tile12 never sends SOUTH to tile8 at steps
   that tile8 needs. Same pattern of broken routes exists throughout the YAML.

E) TILE 9 PHI_START:
   indices 4,5,6 also use routing ports (NORTH, WEST) as first operand,
   with similar bootstrap/routing issues.

CONCLUSION: The entire YAML needs to be REWRITTEN with correct direction
conventions. Patching individual routes won't work because the scheduling
depends on the routing topology. A single direction swap cascades into
broken timing throughout the pipeline.

7. KEY ARCHITECTURE DETAILS FOR YAML GENERATION
═══════════════════════════════════════════════════════════════════════

A) PHI_START behavior (fu/single/PhiRTL.py):
   - first=1 (iteration 0): Uses recv_in[in0_idx] ONLY. Validation:
       recv_all_val = first & recv_in[in0_idx].val
   - first=0 (subsequent): Uses predicate-based selection between in0 and in1.
       recv_all_val = ~first & recv_in[in0_idx].val & recv_in[in1_idx].val
       Both inputs must be valid!
   - first flag cleared when ctrl_addr wraps (ctrl_addr < prev_ctrl_addr).
   
   PATTERN FROM WORKING spmv.yaml:
     PHI_START always uses REGISTERS for both operands (not routing ports).
     PHI_START second operand gets a routing crossbar prologue if it's a PORT.

B) PHI_CONST behavior:
   - first=1: Uses recv_const (from const queue)
   - first=0: Uses recv_in[in0_idx] ONLY (no predicate check)
   - NOT suitable for loop PHIs that need predicate-based selection!

C) GRANT_ONCE (fu/single/GrantRTL.py):
   - Sets output value and predicate=1 on FIRST execution.
   - Subsequent executions: predicate=0 (already_grt_once flag).
   - IS a FU operation (takes up the FU for that step).
   - Only one GRANT_ONCE per step per tile.

D) GRANT_PREDICATE:
   - Takes two inputs, ANDs the second input's predicate onto the first.
   - Used to propagate loop control predicates to PHI operands.
   - IS a FU operation.

E) invalid_iterations:
   - When > 0, generates prologue packets that make the tile skip the operation
     during the first N iterations.
   - The prologue mechanism tells the FU and crossbars to ignore certain
     operations during the pipeline fill phase.

F) LOAD/STORE memory access:
   - LOAD src_operands[0] = address (from FU input). Result goes to FU output.
   - The actual memory R/W goes through to_mem_raddr/from_mem_rdata, connected
     to the tile's memory port (WEST for col 0, SOUTH for row 0 col>0).
   - STORE src_operands[0] = address, src_operands[1] = data.

G) DATA_MOV:
   - PORT → PORT: Uses routing crossbar ONLY (no FU needed)
   - PORT → REG: Uses routing crossbar ONLY (no FU needed)
   - REG → PORT: Uses register read + routing crossbar (no FU needed)
   - Multiple DATA_MOVs can co-exist at same step with a FU operation.
   
H) Multiple dst_operands:
   - A single FU operation can output to multiple ports/registers.
   - FuOutParams[port_idx] = 1 for each active output port (multicast).

I) Const queue:
   - Operations with #imm operands consume from the const queue.
   - Constants are preloaded in order via CMD_CONST packets.
   - The script_generator handles this automatically from the YAML.

J) Register allocation:
   - num_registers_per_reg_bank = 8
   - $0..$7 = cluster 1, $8..$15 = cluster 2
   - Two clusters can be read/written independently per cycle.
   - Collision: two registers in the same cluster can't be read/written
     in the same cycle for different purposes.

9. REFERENCE: WORKING spmv.yaml PATTERNS
═══════════════════════════════════════════════════════════════════════

The spmv.yaml at validation/test/spmv.yaml is a WORKING kernel.
Key patterns to follow:

a) PHI_START always uses REGISTERS for both operands:
   PHI_START $0, $8 → dst   (not PHI_START SOUTH, $8 → dst)

b) GRANT_ONCE initializes registers before PHI_START:
   Step N:   GRANT_ONCE #value → $reg
   Step N+M: PHI_START $reg, $loopback → dst

c) Multiple dst_operands for multicast:
   PHI_START $0, $8 → EAST, NORTH, $0   (sends to 3 destinations)

d) invalid_iterations for pipeline prologue:
   Operations that depend on previous iterations use invalid_iterations: 1
   (or higher). The FU and crossbars are prologued to skip these.

e) CTRL_MOV for cross-iteration register writes:
   CTRL_MOV EAST → $8   (with invalid_iterations: 1)
   Writes the loopback value from a routing port into a register,
   starting from iteration 1.
